OwnTV · Sync design proposal

Skip-sync: never spend time on sections you don't want

Today every Live / Movies / Series section of an Xtream source is always synced - the only choice is now vs in the background. This adds a real third state, Off, so a user can tell OwnTV to never fetch a section at all - saved on the source, and honored on every add, re-sync and auto-refresh.

Xtream (primary) Stalker (same model) DB v16 → v17 migration TV D-pad UI No behavior change for existing sources

01 The gap today

The add / re-sync flow already models three content types as SyncContentTypes(live, movies, series), but a checkbox only routes a type to the foreground (now) or the background remainder (later). There is no way to say "don't sync this." Unchecking still syncs it - just later.

What "off" does today

runImport() passes checked types as the priority foreground pass; SyncContentTypes().remainderAfter(priority) computes everything not checked and enqueues it to CatalogSyncWorker. The remainder always covers the full catalog.

Re-sync ignores the choice entirely

SettingsViewModel.resync() and ShellViewModel.checkAutoRefresh() enqueue with the default SyncContentTypes() = all-true. So even a "later" choice is forgotten on the next sync - every re-sync pulls all three sections.

Nothing is persisted

The three booleans live only in the Add screen's local state. SourceEntity stores no per-section scope, so there is nowhere for "skip Series forever" to live.

02 Proposed UI — a three-way scope

Replace the binary "Sync first" toggles with a segmented Now / Later / Off control per section. On the Edit screen (and implicitly on re-sync) it collapses to On / Off, since "now vs later" only means something during the very first import.

Q "Do these three sections already exist, or do we add the sections themselves?"

They already exist - we only add the toggle. Live / Movies / Series are first-class MainSection entries (LIVE_TV, MOVIES, SERIES) with their own browse screens and view-models, and the add form already shows the three Live/Movies/Series toggles today. The nav even hides a section when the source has none of that type (if (hasMovies) add(MOVIES)). So this is a toggle upgrade + a persisted flag, not a new content pipeline.

03 Behavior: current vs target

The single new rule: an Off section is subtracted at every entry point, not just at add time.

Entry pointTodayWith skip-sync
Add source Checked = foreground, unchecked = background remainder. All 3 always sync. Now = foreground · Later = remainder · Off = never enqueued. Scope saved to SourceEntity.
Manual re-sync Always full catalog (defaults to all-true), ignoring the add-time choice. Reads the saved scope → syncs only On sections.
Auto-refresh Always full catalog on staleness / startup. Reads the saved scope → Off sections stay untouched.
Background worker Syncs whatever contentTypes the enqueue carried. Intersects the enqueue with the source's saved scope as the source of truth - a stale enqueue can never revive an Off section.
Turn a section Off later n/a Catalog rows purged so nothing stale lingers; per-profile progress & favorites are snapshotted to the persisted pending store, not deleted. Re-enable + resync re-attaches them (existing resolvePending path).
Existing sources (migration) n/a All 3 default to On → identical to today. Zero behavior change until edited.

04 How a scope routes a section

One decision per section, applied identically whether the trigger is a fresh add or a scheduled refresh.

05 Implementation plan

Small, additive, and centered on one idea: persist the enabled set on the source, then make every sync entry point subtract the disabled sections.

  1. Persist scope on SourceEntity

    Add syncLive, syncMovies, syncSeries booleans (default true). This is the enabled set = On sections; Off = false. "Now vs later" is not stored - it's a transient first-import-only priority.

    core/database/entity/ProfileEntities.kt

  2. DB v16 → v17 migration

    Three ALTER TABLE sources ADD COLUMN … NOT NULL DEFAULT 1, mirroring the v13→v14 sources.mac migration. Existing rows become all-On = today's behavior.

    core/database/OwnTVDatabase.kt

  3. Make the remainder relative to the enabled set

    Add SyncContentTypes.enabledOf(source) and change the remainder from SyncContentTypes().remainderAfter(priority) (full − now) to enabled.remainderAfter(priority) (enabled − now). Off sections drop out of both the foreground pass and the remainder.

    core/sync/SyncStatus.kt · SetupViewModel.kt · SettingsViewModel.kt

  4. Honor scope on re-sync & auto-refresh

    resync() and checkAutoRefresh() pass enabledOf(source) as contentTypes instead of the default all-true.

    SettingsViewModel.kt:754 · ShellViewModel.kt:168

  5. Worker treats saved scope as source of truth

    CatalogSyncWorker intersects the input contentTypes with the source's saved flags, so a queued job from before an edit can't fetch a now-Off section. Slots next to the existing M3U/backup override.

    core/sync/work/CatalogSyncWorker.kt:55

  6. Turn Off: purge catalog, keep progress & favorites

    On Edit save, diff old vs new scope. For each newly-Off type: (1) snapshot that section's user data via exportForSource(id, kinds) into the persisted pending store, (2) clearSource only its catalog rows. Do not run the destructive orphan-purge (it's gated on a full-catalog success anyway). Newly-On triggers a scoped resync; resolvePending re-attaches progress as the rows reappear - the exact mechanism that already survives clear-then-insert churn. Favorites/history/progress FK only to the profile, so nothing cascades.

    UserDataResolver.kt (exportForSource / resolvePending) · SourceRepository.clearSourceContent:71

  7. UI: segmented control + Edit-form scope

    New SyncScopeRow composable (Now/Later/Off on add, On/Off on edit) replacing the three ToggleRows. Show the scope section when editing an Xtream/Stalker source too (today showContentToggles hides it on edit).

    features/setup/AddSourceScreen.kt:280

  8. Carry scope through the plumbing

    Thread the enabled set through onStartXtream → SetupViewModel.startXtream / SettingsViewModel.addXtream → addXtreamSource. Extend the companion (phone) add-form's existing syncLive/syncMovies/syncSeries to a tri-state where relevant.

06 Risks & edge cases

🧭

All-Off must stay impossible

Keep the existing guard - Start Import disabled unless at least one section is On. On the Edit form, block saving an all-Off source (it would be an empty, contentless source).

🗑️

Purge the catalog only - never the user data

Clear only the toggled type's catalog rows for the one source (never other sources on the profile). Favorites/history/progress must be snapshotted to pending first, and the full-catalog orphan-purge must stay off for a scoped change. A short "Movies catalog will be cleared; progress kept" confirm sets expectations without implying data loss.

📺

M3U is single-stream

M3U/backup sources are live-only in the worker already, so the scope UI is Xtream/Stalker only - don't surface Now/Later/Off for M3U.

💾

Backup round-trip

Include the three flags in BackupManager export/import so a restored source keeps its skip choices instead of silently re-syncing everything.

🏠

Empty section in the shell & on Home

The sidebar already hides a section when the source has none of that type (if (hasMovies) add(MOVIES)), so an Off section drops out of nav for free. Remaining work: make sure the Home screen rails (recently-added Movies/Series, continue-watching) degrade gracefully when a whole section is intentionally absent - hide the empty rail rather than showing a blank shelf.

Q "Can we drop the Series/VOD catalog but keep progress, and restore it on re-enable? If not possible, skip it."

Possible - and it's how the app is already built, so we do it. Favorites, watch history and resume positions FK only to the profile (never to content rows), and they're keyed to content by a stable identity, not the volatile row id. Records that can't resolve sit in a persisted pending store (PENDING_KEY in DataStore) and "heal after every sync as content appears." So turning Movies/Series Off snapshots its user data to pending and clears only the catalog; turning it back On + resync re-attaches progress via the existing resolvePending path. No new persistence layer needed.
