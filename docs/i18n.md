# OwnTV i18n authoring guide

> A string used for comparison, parsing or protocol behaviour is a key, not a display label. Never
> translate it in place.

This is the day-to-day guide for adding and changing user-facing strings. The full plan, including
the verified Android locale mechanics and the phase roadmap, lives in
[`docs/internationalization.md`](./internationalization.md). Read that first if you are touching the
locale runtime, the guardrails or the named non-Compose renderers.

## Where the localisation boundary sits

**Only the presentation layer speaks the user's language.** Application, domain, repository, Worker
and persistence code emit semantic facts, counts, identifiers and raw external content; they do not
produce resolved translated sentences merely because they run outside Compose.

- **Compose** resolves everything it ultimately renders, via `stringResource` / `pluralStringResource`
  / `stringArrayResource`.
- A small **named set of final renderers** resolves user-facing output that Android or the companion
  server renders outside Compose: `CompanionHtml`, download notifications, the existing system
  toast / chooser sites in `OwnTVPlayer` / `ExternalPlayerLauncher`, and the legacy Android TV
  launcher publisher. Each wraps a locale context **at render or publish time** and reads the
  **current** `LocaleStore` value, never a startup-captured one.
- **Nothing else** may resolve resources. A repository or Worker is not a final renderer just because
  it runs in the background. There is no process-wide `UiText` abstraction and no
  `LocaleContextProvider`; v2 removed both.

If you are outside Compose and need a sentence, first ask whether you are one of the named final
renderers. If not, emit typed semantic state and let Compose word it.

## How to add a string

1. Pick the right split file by area:

   | File | Holds |
   |---|---|
   | `values/strings.xml` | common actions, buttons, generic errors |
   | `values/strings_setup.xml` | onboarding, add-source, companion |
   | `values/strings_settings.xml` | all settings screens |
   | `values/strings_player.xml` | player HUD, tracks, diagnostics |
   | `values/strings_content.xml` | home, live, movies, series, epg, search, downloads, subtitles |
   | `values/strings_features.xml` | profiles, home rows, search and launcher copy |
   | `values/strings_phase1.xml` | phase-one settings, EPG, downloads, subtitles and companion copy |
   | `values/donottranslate.xml` | brand + protocol constants, `translatable="false"` |

2. Name it `<area>_<screen>_<element>[_<variant>]`, snake_case: `settings_network_proxy_invalid_port`,
   `player_error_both_engines_failed`. Shared strings use the `common_` prefix.

3. Add the English source to the chosen file in `values/`. Weblate's component-discovery addon pairs
   each `values-<x>/strings*.xml` with its base file in `values/`, so translations land automatically.

4. If the key is non-obvious, add a `comment=` attribute and wrap placeholders in `<xliff:g>` —
   Weblate shows both to translators.

5. Run `python3 tools/i18n/gen_supported_locales.py` to refresh `SupportedLocales.kt` (coverage is
   computed), then `python3 tools/i18n/validate_strings.py`. Release CI invokes
   `python3 tools/i18n/validate_strings.py --release` so packaged translations also need explicit
   review state. CI runs `gen_supported_locales.py check` (which fails if the checked-in
   `SupportedLocales.kt` is stale relative to `locales.json` and the resource tree), so a PR that
   edits either must regenerate.

6. **Delete the literal you replaced from `tools/i18n/hardcoded_baseline.txt`** by re-running
   `python3 tools/i18n/check_hardcoded_strings.py generate`. The baseline may only shrink; the CI
   guard fails if a PR-head literal is absent from the merge-base baseline. The checker inventories
   every Kotlin literal without guessing its meaning. A new developer-only value must be explicitly
   classified in `tools/i18n/safe_literals.txt` with:
   `python3 tools/i18n/check_hardcoded_strings.py classify-safe --path <file> --text <text> --category <category>`.

## Authoring rules

- **Always positional (`%1$s`), never bare `%s`.** Translators must be able to reorder.
- **One string per sentence. Never concatenate fragments.** Build a full parameterised sentence
  instead of gluing a noun into a template — the noun's case, gender and plural agreement differ by
  language. The documented exception is structured metadata joins (`Title · Year · Rating`), which
  happen at the presentation boundary only, from already-localised parts, with a separator that is
  not itself translated.
- **`<plurals>` for anything counted, never `"s"`-suffix branching.** Android resolves quantities
  through bundled ICU (`PluralRules.forLocale`) on API 24+, so full CLDR rules (Arabic's 6 forms,
  Polish's 4, Russian's 3) are free. Exactly six valid keywords: `zero one two few many other`.
  **`other` is mandatory in every `<plurals>`** or lookup throws `NotFoundException` at runtime;
  `validate_strings.py` enforces it.
- **A string used for comparison, parsing or protocol behaviour is a key, not a display label. Never
  translate it in place.** (See the block at the top of this file.) Split a value that is used for
  both: keep a stable canonical key and add a separate `@StringRes` display label, or map the enum to
  resources in a UI package.
- `translatable="false"` for brand and protocol strings, and keep those in `donottranslate.xml`, not
  in `strings*.xml`.
- `<xliff:g>` around placeholders and a `comment=` attribute on any non-obvious key.
- **Never persist a resolved translation or a resource ID.** Persist raw provider text, stable
  identifiers, domain values, counts and timestamps. A German sentence must never be restored onto an
  English device; a persisted `R.string.*` id outlives the install that created it and is not stable
  across builds.

## The `ErrorMessages` English-needle caveat

`core/util/ErrorMessages.kt` matches internally-thrown exception **needles** (e.g. `"MAC may not be
authorized"`, `"Portal handshake"`, `"timeout"`) to classify failures. Those needles are **stable
comparison keys and stay English forever** — translating a thrown message silently breaks
classification. Document the invariant at both the throw site and the classifier, and the strings are
listed explicitly under the `protocol` category in `safe_literals.txt`. Translating the *friendly output* of a
classified failure happens only at the Compose presentation boundary.

## Where the locale runtime lives

`core/i18n/` owns:

- `LocaleStore` — the single SharedPreferences-backed authority. `""` means "follow the current
  device locale list". Every locale write (picker, reset, backup import) goes through `LocaleStore.set`,
  which persists, publishes the `StateFlow`, AND calls `AppLocale.applyGlobally` so `java.text` /
  `java.time` / `String.format` / `Locale.getDefault()` readers follow the new selection immediately —
  not on the next unrelated configuration callback.
- `AppLocale` — `wrap(base, tag)` for a locale context, `wrapForCompose(base, tag)` for an
  Activity-preserving Compose context, and `applyGlobally(tag)` for the process `Locale`/`LocaleList`
  defaults (consumed by `java.text` / `java.time` / `String.format`).
- `LocalizedContent` — the Compose wrapper providing the four locale locals and triggering the one
  documented `Activity.recreate()` across a script-family boundary.
- `SupportedLocales` — the generated catalogue (from `tools/i18n/locales.json` + computed coverage).

## Translating

Translations are managed on Weblate (see the Phase 4 section of the plan). Do not hand-edit
`values-<x>/strings*.xml` for translations in normal work; push source English and let Weblate sync.
A `CONTRIBUTING.md` section will point translators at the Weblate project once it is configured.

For release-packaged locales, the checked-in `tools/i18n/translation_status.json` records the state
Weblate/release review assigned to each translated resource key. The validator accepts only
`translated` or `approved`; `needs-editing`, `needs-review`, `untranslated` and missing states fail
release validation. It intentionally does not compare translated text with English: `OK`, `TV`, `PIN`,
Wi-Fi and brand names can be valid unchanged translations.
